## 1. プロジェクト概要
* **プロジェクト名**: iezi
* **アーキテクチャ方針**: 完全オンデマンド型サーバーレスアーキテクチャ
* **運用コスト目標**: ユーザー2名による日常利用において、AWS無料枠を最大限活用し、維持費（固定費）を極限まで排除した月額ほぼ0円での運用を目指す。

## 2. 全体システムアーキテクチャ
本プロジェクトは、可用性・スケーラビリティの確保と運用負荷の最小化を両立するため、フロントエンド、認証、API受付、コンピューティング、データベースのすべてにAWSのフルマネージドサービスを採用します。

### 2.1. システム構造図（データフロー概略）

```
[User Browser] ──(HTTPS)──> [Amazon S3] (静的ホスティング)
│
(API Request / JWT)
▼
[Amazon API Gateway] (Cognito Authorizerによる入口での認証検証)
│
(安全なコンテキスト / CognitoSub の伝播)
▼
[AWS Lambda (メインAPI)] (Go言語ファットLambdaによるビジネスロジック処理)
│
(データ永続化 / トランザクション処理)
▼
[Amazon DynamoDB] (シングルテーブル設計)
│
(DynamoDB Streams / 非同期トリガー)
▼
[AWS Lambda (集計用)] (バックグラウンドでのポイント自動更新処理)
```

### 2.2. リポジトリ構成（モノレポ）
インフラとアプリケーションコードの密結合性を担保し、環境構築の再現性を高めるため、1リポジトリで一元管理するモノレポ構成を採用します。
* `frontend/` : React (SPA) アプリケーション
* `backend/` : Go言語によるLambdaソースコード
* `infrastructure/` : TerraformによるHCLインフラストラクチャ定義

## 3. インフラコンポーネント仕様

### 3.1. フロントエンド配信層（Amazon S3）
* **役割**: Reactでビルドされた静的アセット（HTML, CSS, JavaScript, 画像等）のホスティング。
* **構成方針**: サーバーサイドレンダリング（SSR）を行わない完全なSPA（シングルページアプリケーション）構成とし、S3からの直接配信を行うことで、計算リソースの維持費をゼロにします。

### 3.2. API・ルーティング層（Amazon API Gateway）
* **役割**: クライアントからのREST APIリクエストの受付、およびバックエンドへのプロキシ。
* **構成方針**: `ANY /{proxy+}` 設定を用いたLambdaプロキシ統合を採用。エンドポイントごとの詳細なルーティングはインフラ側で個別定義せず、コンピューティング層へ透過的に引き渡します。
* **アクセス保護**: Cognito Authorizerを前面に配置し、APIの境界線で不正なリクエストをシャットアウトします。

### 3.3. コンピューティング層（AWS Lambda）
* **役割**: アプリケーションのビジネスロジックの実行。
* **構成方針**: 完全オンデマンド起動によるリクエスト課金。以下の2つのコンポーネントに分離します。
  1. **メインAPI用Lambda (ファットLambda構成)**: 全てのエンドポイントの処理ロジックを単一の関数に集約。Go言語の「コンパイルによる単一バイナリ生成の恩恵（爆速なコールドスタート性能）」を活かし、インフラ定義のシンプル化と開発体験の向上を両立します。
  2. **ポイント集計用Lambda**: データベースの変更イベントを検知して非同期で起動する、バックグラウンド処理専用の独立した関数です。

### 3.4. データベース層（Amazon DynamoDB）
* **役割**: アプリケーションデータの永続化。
* **構成方針**: 1つの物理テーブルにあらゆるエンティティを同居させる「シングルテーブルデザイン」を採用します。
  * **主キー設計**: パーティションキー（PK）とソートキー（SK）を組み合わせた複合主キー。PKに家族（グループ）の一意なIDを据えることで、同一グループ内のデータを物理的に近接させ、クエリを高速化します。
  * **データライフサイクル管理 (TTL)**: レコードごとに個別に有効期限（UNIXタイムスタンプ）を保持可能なTTL（Time To Live）機能を有効化。日次サマリやログ履歴などの肥大化しやすいデータに対し、自動削除プロセスを適用してストレージコストを最適化します。
  * **イベント駆動連携**: DynamoDB Streamsを有効化し、データの変更（挿入・修正・削除）イベントを集計用Lambdaへ非同期にストリーミングします。

### 3.5. 認証・認可層（Amazon Cognito）
* **役割**: ユーザー管理、サインアップ/サインイン認証、およびセキュリティトークン（JWT）の発行。
* **構成方針**: 完全に独立した認証プロバイダーとしてCognitoユーザープールを運用。フロントエンドへの認証UIの提供から、安全なセッション管理までをフルマネージドで委ねます。

## 4. セキュリティ & データ整合性設計

### 4.1. 認証ガードによるコスト・セキュリティ防御
フロントエンドからHTTPヘッダー（`Authorization`）で送られてくるJWTは、API GatewayのCognito Authorizerによって入り口で自動検証されます。
署名切れや不正なトークンは、奥にあるLambdaを起動させる前に「401 Unauthorized」として門前払いするため、悪意あるリクエストやバグによる無駄なLambdaの起動・課金を根本から防御します。また、検証済みの安全なユーザー識別子（`CognitoSub`）は、API GatewayからLambdaへ安全に引き渡されます。

### 4.2. 個人情報（PII）の分離（セパレーション）
メールアドレスやパスワードなどの個人情報（PII: Personally Identifiable Information）は、すべて堅牢なAmazon Cognito側に安全に格納・秘匿します。
アプリケーションのメインデータベース（DynamoDB）側には、個人を特定できないランダムなUUID形式の識別子（`CognitoSub`）のみを「UserID」の背番号として保持させることで、万が一のデータ漏洩時にも実世界の個人情報と結びつかない強固なセキュリティ分離を実現します。

### 4.3. エンドツーエンドでの冪等性（二重操作・リトライバグ防止）
通信エラーによるリトライや、ユーザーによるボタンの連打が起きても、データの不正な重複登録やポイントの二重加算（バグ増殖）を100%防止するため、フロントからDBまで一貫した冪等性ロジックをインフラレベルで担保します。
1. **フロントエンド**: 操作が発生した最初の瞬間に、一意なアクションID（UUID）を発行してリクエストに付与。自動再送時も同じIDを使い回します。
2. **バックエンド**: Lambdaは受け取ったIDをデータベースの主キー（SK）の一部としてそのまま組み込みます。
3. **データベース**: DynamoDBへのトランザクション書き込み時に「対象キーがまだ存在しない場合のみ書き込みを許可する条件式（Conditional Write）」を適用。2回目以降の重複リクエストが届いた場合は、インフラ（DynamoDB）の制約によって安全に処理を弾き、データの整合性を死守します。

## 5. IaC（インフラのコード化）& 環境管理仕様

### 5.1. Terraformによるリソース管理
すべてのAWSリソースはTerraform（HCL）を用いてコード化し、環境の再現性と構成の透明性を確保します。
* `provider.tf` : AWSプロバイダー、リージョン、共通環境変数の定義
* `dynamodb.tf` : テーブル（`FamilyAppTable`）、TTL属性、DynamoDB Streamsの設定
* `cognito.tf` : ユーザープールおよびクライアントアプリケーションの設定
* `lambda.tf` : 各Lambda関数のIAMロール、実行環境、トリガーの定義
* `apigateway.tf` : プロキシ統合、CORS、Cognito Authorizerの定義

### 5.2. 環境分離方針
開発・検証用の「ステージング（Staging）環境」と、日常利用を行う「本番（Production）環境」の2つを定義。Terraformのワークスペース（Workspace）機能、または環境ごとの変数ファイル（`.tfvars`）を用いて同一のテンプレートコードから完全に隔離された独立のインフラ環境をデプロイ・管理します。

### 5.3. シークレット管理とオブザーバビリティ
* **シークレット管理**: APIキーや環境変数、AWSへのデプロイに必要なクレデンシャル情報は、GitHub ActionsのGitHub SecretsやAWS Systems Manager（Parameter Store）を活用し、ソースコードに埋め込むことなく安全に注入します。
* **ログのライフサイクル管理**: デバッグおよび運用監視のため、Lambda等の実行ログをAmazon CloudWatch Logsへ集約。ただし、ストレージ料金の永続的な累積課金を防ぐため、すべてのロググループに対して保持期間（Retention）を14日〜30日程度に制限するライフサイクルポリシーをインフラ定義側で強制します。
