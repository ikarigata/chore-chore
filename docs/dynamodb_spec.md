# iezi (家事管理アプリ) DynamoDB テーブル仕様書

## 1. テーブル基本設定

* **テーブル名** : FamilyAppTable（※完全な1テーブル運用）
* **パーティションキー (PK)** : FamilyID (String)
    * 家族単位でデータを同じ物理サーバーにまとめることで、アクセスを高速化します。
* **ソートキー (SK)** : DataSortKey (String)
    * プレフィックス（接頭辞）を活用し、同じPKの中で「設定データ」や「履歴データ」を同居させ、前方一致や範囲指定で柔軟に検索します。

## 2. データモデル（エンティティ別プレフィックス設計）

大前提として、PKはすべて共通の FamilyID になります。SKのプレフィックスで以下のデータを区別・同居させます。

### ① ユーザー情報

* **ソートキー (SK)** : USER#{CognitoSub}
* **用途** : パパ、ママ、子どもなどのメンバー情報（表示名、アイコンURLなど）を保持します。
* **仕様** : CognitoSubは個人情報を含まず不変であるため、ユーザーを一意に特定するIDとして安全にそのまま使用します。TTLは設定しません（永久保存）。

### ② 家事のマスター設定

* **ソートキー (SK)** : TASK#{TaskID}
* **用途** : 家事の設定（例：お風呂掃除は10ポイント、など）の定義データを保持します。
* **仕様** : TTLは設定しません（永久保存）。

### ③ 日次サマリ（ホットデータ）

* **ソートキー (SK)** : DAILY#{YYYY-MM-DD}#{CognitoSub}
* **用途** : その日のタスク完了状況や獲得ポイントの合計を保持します。
* **重要な仕様（タイムゾーン）** : 日付の境界を厳密に管理するため、Lambda（Go）側で必ず Asia/Tokyo などの指定タイムゾーンで日付文字列（YYYY-MM-DD）を生成します。
* **重要な仕様（データライフサイクル）** : 無限にデータが溜まるのを防ぐため、Lambdaでの作成時に現在時刻から一定期間後（例：90日後）のUNIXタイムスタンプを計算し、ExpiresAt 属性にセットしてTTL（自動削除）の対象とします。

### ④ タスク履歴（コールドデータ）

* **ソートキー (SK)** : HISTORY#{RFC3339Timestamp}#{CognitoSub}#{TaskExecutionID}
* **用途** : 誰がいつ家事を実行したかのタイムライン表示などに使用します。
* **重要な仕様（TTL）** : テーブルの属性に ExpiresAt (Number型) を追加してUNIXタイムスタンプを格納し、AWS側のTTL機能の対象として明記します（例：完了から1年後に自動削除）。

## 3. 最重要ロジック：冪等性（ポイント増殖バグ防止）の仕様

通信エラーによるLambdaの自動リトライや、ユーザーのボタン連打による「ポイントの二重加算」をシステム全体で完全に防ぐための仕様です。

1. **フロントエンドでのUUID発行と状態保持** :
    * ユーザーが家事の「完了ボタン」を初めてタップした瞬間に、フロントエンドでUUID v4（TaskExecutionID）を生成します。
    * 画面をローディング状態にして連打を防ぎつつ、通信エラー等で自動リトライする際は、新しいIDは作らず 1回目に生成したUUIDを使い回して再送 します。
2. **SKへの組み込み** :
    * 送られてきたUUID（TaskExecutionID）は、タスク履歴のSKの末尾に組み込まれます。
3. **バックエンドでの条件付き書き込み** :
    * LambdaがDynamoDBへトランザクション書き込み（TransactWriteItems）を行う際、「もしこの HistoryKey がまだ存在していなければ書き込む（attribute_not_exists(HistoryKey)）」という条件を指定します。
4. **確実なブロック** :
    * Lambdaが自動リトライされてもフロントから送られるUUIDは同じであるため、2回目以降の書き込みはDynamoDBの条件チェックで弾かれ、ポイントの二重加算を確実に防ぎます。
